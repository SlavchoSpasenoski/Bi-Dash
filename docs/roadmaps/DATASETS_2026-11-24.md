# Bi-Dash Datasets roadmap

Prepared 2026-11-24. This document defines proposed implementation and release criteria.

The first release was activated locally on 2026-11-25 for direct MySQL/MariaDB. See [STATUS.md](../../STATUS.md) for verified scope, migration and release evidence.

## Prototype boundary

The compiler in `redash/dataset_sql.py` starts with one table and an explicit column projection, optional aliases and simple filters. It compiles structured arithmetic over base fields. Its catalog-backed entry point resolves source names and checks native type, precision and scale. Product integration must authorize the base query before catalog discovery and validate the actual composed query against current access policy before executing it.

The prototype rounds division ties away from zero using the exact remainder. Boundary fixtures passed on PostgreSQL, MySQL and MariaDB. PostgreSQL raises on an out-of-range DECIMAL(38,10) cast. MySQL and MariaDB can return a saturated value with a warning. The shared MySQL runner can now discard the entire result when the statement raises a warning, and Dataset execution must opt in. Recheck source-derived precision and scale before publishing and when executing a published formula.

Use a dedicated Dataset provenance marker in saved-report execution. Check it before falling back to existing Query result provenance or latest-result rules. Carry the Dataset, pinned base revision, report revision and current actor context through enqueue, worker, cache and download. Reader refresh must go through the existing dashboard-bound flow without receiving the Dataset definition.

The draft authoring service currently validates and previews up to 50 rows on direct MySQL/MariaDB connections through the shared read-only runner. Publishing pins the saved Query revision after the same validation. Both operations have Dataset job endpoints and use ordinary Query admission. PostgreSQL authoring, browser views and full report result validation remain integration work.

## First release

Add **Datasets** alongside **Queries** and **Dashboards**. Start from a saved query through **Create dataset**, define display names, field types and supported row-level formulas in a draft, preview the result, then publish. **Create chart** opens a builder with field selection, typed filters, grouping and SUM, COUNT and AVG. Save the report as a Dataset-backed Query and reuse existing visualizations and dashboard widgets. Two authorized Editors must be able to build separate charts from the same published model without editing SQL or copying the formula.

## Permission hierarchy

Use Query ownership and source authorization for editing and execution, and Dashboard-style explicit user/group grants for Dataset discovery and reuse. These are proposed Dataset rules aligned with [Access Control](../../ACCESS_CONTROL.md) and [Dashboard Access](../../DASHBOARD_ACCESS.md).

| Action | Organization Admin | Owner Editor | Other Editor | Reader |
| --- | --- | --- | --- | --- |
| Discover and open Dataset definitions | Same-org active Datasets, including drafts, subject to existing Admin source rules | Own active Datasets, with current base-query and source access | Explicitly assigned published Datasets, directly or through a group, with current base-query and source access | No |
| Create, edit, preview drafts and publish | Same-org scope under existing Admin source rules | Own Datasets with Full source access and validated dependencies | May create and publish a separate owned Dataset from an eligible accessible query with Full source access | No |
| Manage Dataset viewers | Any same-org Dataset | Own Dataset, following Dashboard ownership rules | No | No |
| Create or change a Dataset-backed Query | Same-org resources under existing Query rules | Own Queries with Full source access | Own Queries with Full source access and Dataset assignment | No |
| Run a saved Dataset-backed Query | Existing authorized saved-query path | Existing saved-query path, including View only for safe saved definitions | Same as owner Editor, plus Dataset assignment | Only through an assigned published dashboard, with current source and report authorization |
| Download results | Existing export and result rules | Existing export and result rules | Existing export and result rules | Only through an authorized report with export permission |

- Reader dashboard access is scoped to the saved report. It exposes authorized results and display labels, while Dataset definitions, formulas, SQL, source schemas and authoring endpoints stay inaccessible. A Reader uses the dashboard grant and source checks for this flow. An Editor consuming a Dataset-backed report also needs current Dataset access.
- Dataset grants confer use of the published model. Source membership, protected columns, base-query access, Query ownership and Dashboard grants remain independent. A chart author's Full access never executes work on behalf of a viewer. Grants are same-org, publication-bound and evaluated against current group membership. Demotion removes authoring rights, including for former owners. Disabled users and anonymous report tokens are denied.
- Resolve access through shared server predicates. Apply them to lists, search, counts, detail, history, preview, builder, dashboard, enqueue, worker, poll, result and downloads. Recheck after queued work starts and before returning results. Validate the actual saved definition with current rules even when a previous revision was approved. Preserve quotas, timeouts and read-only execution.

## Delivery milestones

1. **Execution and correctness prototype.** Use disposable PostgreSQL, MySQL and MariaDB sources. Prove a supported saved SELECT can be composed without changing its row set, field types or cardinality. Start with an explicit projection over a single saved query. Require stable, unique output names and resolved typed dependencies, including columns used by the base query in filters, joins or other expressions. Reject unsupported SQL shapes and unsafe or unresolved parameters with actionable errors. Offer a dialect only after its parity and access tests pass. Protected-source support must go through the existing applicable policy compiler and runner. Query Results/SQLite is unsuitable for this path because it denies protected dependencies and converts decimals to floating point.
2. **Dataset lifecycle and permissions.** Add same-org ownership, revisioned user/group grants, drafts and immutable published versions. Store stable field IDs, typed expressions, dependencies and the referenced base revision. Compile a bounded, allowlisted expression tree server-side. Document supported operators, precision, NULL propagation and zero-division behavior before exposing formulas. Record audit events for publishing and sharing. Implement optimistic draft saves and atomic publish. Show affected reports before publishing. Block breaking edits to used fields and block archive while active reports depend on the Dataset. Revalidate current source policy against pinned revisions. A changed or archived base query must produce an explicit dependency state where the saved revision can no longer execute safely.
3. **Builder and existing report integration.** Store a structured report definition with Dataset and field references. Server-side generation is authoritative. Reuse existing Query/result, visualization and dashboard components. Track Dataset revision, base revision, report definition, parameters and current authorization in job/result provenance. On compatible publication, dependent reports adopt the new revision on subsequent runs. Cache reads and in-flight jobs from the old revision cannot be presented as current. Include a visible dependency error for affected widgets and preserve the rest of the dashboard.
4. **Release readiness.** Use an additive metadata migration and a rollout flag. Include Dataset-backed content in selective migration only when versions, dependencies and destination permissions can be represented safely. Until that support ships, block export of affected selections with an explicit dependency message. Apply and rehearse rollback on disposable metadata snapshots, preserving existing records, grants and credentials. Update user and access guides before enabling the feature.
5. **Later modeling work.** Add reusable aggregate formulas with explicit grouping and filter order, then same-source joins with declared cardinality and checks for duplicate facts. Cross-source datasets and materialization require a separate design for freshness, precision, storage and policy inheritance.

## Required verification

| Layer | Concrete acceptance checks |
| --- | --- |
| SQL and numerical correctness | Compare generated-query rows and types with independently written reference SQL and expected fixture outputs on each supported engine. Include exact decimal money values, scale/rounding, integer division, NULL, zero denominators, negative values, empty inputs, missing groups, duplicate rows, COUNT(field) versus COUNT of rows, filter boundaries and deterministic dates. Confirm preview and full execution apply the same formula. Specify differences by dialect and fail unsupported operations explicitly. |
| Definitions and schema changes | Cover aliases, renamed display labels, formula dependencies and cycles, duplicate output names, schema drift, base query edits and archives, stale drafts, concurrent publishes, and incompatible field removals. Verify stable IDs keep widgets bound and concurrent conflicts leave the published version intact. |
| Permission matrix | Exercise Admin, owner Editor, assigned and unassigned Editors, Reader, disabled users and another organization. Cover direct/group grants, membership removal, demotion, Full versus View only, export disabled, and a calculated field that depends on a restricted column. Check both visible controls and direct API responses, including metadata and result disclosure. |
| Real worker and cache | Use Redis/RQ and disposable sources. Change grants, source policy or model revision after enqueue and during execution, then check poll, result and download. Verify identity and policy isolation on cold and warm cache, correct parameter binding, timeout/cancellation, retries and rejection of ambiguous provenance. |
| Browser workflow and regression | Use two Editors and an assigned Reader. Publish Sales with Profit, create two independent charts, attach them to dashboards, verify values through refresh and allowed export, then revoke access and repeat. Verify existing ordinary Query and Dashboard paths, including history, role checks, export and migration. Run the existing backend regressions, frontend tests, type checks and Compose validation. |
| Migration and rollout | Verify upgrade, rollback and re-enable on a disposable metadata copy. Compare existing content, ownership, grants and result provenance before and after. Measure preview and grouped query times with representative row counts and record the dataset size, timeouts and limits used. |

Release requires passing evidence per supported engine and entry point, with expected and actual fixture results recorded. Numeric mismatches, unauthorized disclosure, stale authorization or broken existing reports block rollout. Record commands, versions, skips and unresolved issues in STATUS.md. Run integration checks with disposable resources.
